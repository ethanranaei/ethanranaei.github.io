Driver Display & Telemetry Node

What it had to do

  • Read engine channels off the M130 over CAN without adding load that disturbs the bus
  • Drive shift lights with low enough latency that the driver can trust them at redline
  • Log GPS position and IMU motion alongside ECU data for post-session review
  • Survive the vibration, heat, and voltage environment of a running car

How it’s built

Separate FreeRTOS tasks handle CAN receive, sensor polling, and display rendering, so a slow I²C transaction can’t stall the shift-light path. The IMU and peripherals share an I²C bus guarded by a mutex.

The bug worth talking about

The display would intermittently freeze under load. The cause was task priority and I²C bus contention — concurrent access to the shared bus with priorities that let a lower-importance task hold the mutex while the render task waited on it. Fixing it meant reworking both the priority assignment and the mutex scope rather than papering over it with delays.

Failure analysis

After the season I documented what actually failed and why: bad pinning, insufficient strain relief at termination points, and a thermal problem with the ignitor mount.

[FILL: how many failures, where, what the symptom was on-track.]

What changed for the next car

  • Virtual build in harness.design before cutting any wire, so lengths and branch points are decided on a model rather than on the chassis
  • Concentric twisting throughout, for mechanical durability and noise rejection on sensor runs
  • Service loops at every termination so a repair doesn’t consume the wire’s slack
  • Deutsch connectors at the breakpoints
  • Essential and non-essential circuits split, so a non-critical fault can’t take the car off track

Access Control System

A passcode-controlled locking system on a TI TM4C123, written bare-metal in C against the register headers — no HAL, no RTOS. Six peripheral subsystems brought up from scratch and made to work together. ECE 425L, with David Avshalom.

Design decisions

  • Hysteresis on the proximity wake. The photocell threshold uses separate assert and release points (1.2 V / 0.7 V) with a state latch, so the display doesn’t chatter when ambient light sits near the boundary.
  • Debounce with confirm-and-release. Edge detect, 20 ms settle, re-read to confirm, then block until the button is released — rather than trusting a single sample.
  • Timer-gated tone generation. Timer0 in periodic mode at 1 µs ticks sets buzzer frequency, instead of tuning loop counts by ear.
  • Modular bring-up. Each peripheral has its own init and control functions so subsystems could be tested in isolation before integration.

Actuation

The stepper runs an eight-state half-step table on PB0–PB3 through a ULN2003 driver, indexed forward for unlock and reversed for lock. Coils are de-energized at the end of every move so the motor isn’t holding current — and heating — while idle.

The failure that taught the most

The first build used a servo. Under load the system would freeze and reset — but only when the servo moved. The servo, LCD, and buzzer were all drawing from the microcontroller’s supply, and the inrush when the servo started was pulling the rail below the brown-out threshold.

The fix was architectural rather than incremental: move the actuator to a 28BYJ-48 stepper on its own external supply, taking the motor current off the MCU rail entirely. The resets stopped. Correlating “it only fails when the motor moves” to a power-integrity problem, instead of chasing it as a firmware bug, was the real lesson.

What I’d change

The delay functions are busy-wait loops — fragile under compiler optimization and blocking for the whole system. I’d move timing to SysTick and restructure the main loop as a non-blocking state machine, so input stays responsive while the motor runs.
