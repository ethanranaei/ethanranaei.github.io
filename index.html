Access Control System

A passcode-controlled locking system on a TI TM4C123, written bare-metal in C against the register headers — no HAL, no RTOS. Six peripheral subsystems brought up from scratch and made to work together. ECE 425L, with David Avshalom.

Design decisions

  • Hysteresis on the proximity wake. The photocell threshold uses separate assert and release points (1.2 V / 0.7 V) with a state latch, so the display doesn’t chatter when ambient light sits near the boundary.
  • Debounce with confirm-and-release. Edge detect, 20 ms settle, re-read to confirm, then block until the button is released — rather than trusting a single sample.
  • Timer-gated tone generation. Timer0 in periodic mode at 1 µs ticks sets buzzer frequency, instead of tuning loop counts by ear.
  • Modular bring-up. Each peripheral has its own init and control functions so subsystems could be tested in isolation before integration.

Actuation

The stepper runs an eight-state half-step table on PB0–PB3 through a ULN2003 driver, indexed forward for unlock and reversed for lock. Coils are de-energized at the end of every move so the motor isn’t holding current — and heating — while idle.

The failure that taught the most

The first build used a servo. Under load the system would freeze and reset — but only when the servo moved. The servo, LCD, and buzzer were all drawing from the microcontroller’s supply, and the inrush when the servo started was pulling the rail below the brown-out threshold.

The fix was architectural rather than incremental: move the actuator to a 28BYJ-48 stepper on its own external supply, taking the motor current off the MCU rail entirely. The resets stopped. Correlating “it only fails when the motor moves” to a power-integrity problem, instead of chasing it as a firmware bug, was the real lesson.

What I’d change

The delay functions are busy-wait loops — fragile under compiler optimization and blocking for the whole system. I’d move timing to SysTick and restructure the main loop as a non-blocking state machine, so input stays responsive while the motor runs.

Knock sensor interface

The knock sensor is a three-wire part; the M130 input takes two. I re-pinned it to the correct two-wire configuration, then verified on an oscilloscope that the ECU was seeing a correct signal rather than a floating or mis-referenced one.

What I found and fixed

Several terminations on the car were failing in service, and most shared a cause: no strain relief at the termination, so vibration and handling loads went straight into the crimp and broke conductors at the pin.

  • 34-pin MoTeC connector — wires breaking off at the pins. Re-pinned with proper strain relief.
  • 20-pin dashboard connector — connector body damaged. Replaced the connector and re-pinned the circuits into it.
  • Injector 1 — same strain-relief failure mode, re-terminated.
  • AEM ignitor — pinned to the wrong positions and unrelieved. Corrected the pinout and re-terminated.

The takeaway I carry forward: on a vehicle, connections fail at terminations, and they fail mechanically before they fail electrically. Strain relief is not a finishing touch.

The goal

Put live engine and vehicle channels in front of the driver on a TFT panel, with the display logic authored as a Simulink model and generated to C rather than hand-written — so the team can change what’s shown without rewriting firmware.

Where it stands

TouchGFX alone works: the panel initializes and renders images correctly. Bringing in the Simulink-generated code produces a blank screen — the board runs, but nothing draws.

What I’m working through

Because TouchGFX renders correctly on its own, the TFT panel, framebuffer, and LTDC configuration are all known good. That isolates the fault to the integration itself, which narrows it to a few candidates worth checking in order:

  • Generated initialization code re-configuring clocks or peripherals that TouchGFX already set up
  • The model’s step function running in a context that blocks or starves the render task
  • Framebuffer memory overlapping a region the generated code claims
  • The generated code never reaching the draw calls at all — a fault or hang before first render

AXI Quad SPI Bring-Up & Verification

Integrated Xilinx’s AXI Quad SPI IP core on a Zybo Z7-10, drove it over AXI4-Lite in internal loopback, and got a self-checking testbench passing in behavioral simulation. ECE 420 final project, Spring 2026.

The problem

Read the AXI4-Lite specification cold — it wasn’t covered in lecture — and use it to drive a vendor IP core’s register map: configure the SPI control register, load the transmit FIFO, start a transfer, and read the result back.

Verification without external hardware

The core runs in internal loopback: setting the LOOP bit in SPICR routes MOSI back to MISO inside the IP, so no external SPI slave is needed. Transmit 0xA5 and the expected value is definitionally the same byte coming back — a golden value you can prove rather than measure.

Two failures that took real debugging

  • Elaboration error on the clock wizard. The generated MMCM had active-low reset enabled, but the component declaration was missing the resetn port. The tool error pointed at the instantiation; the actual cause was in how the IP had been configured.
  • Simulation hung with the test never passing. The IP had been generated with STARTUPE2 enabled, which internalizes the SPI clock and replaces the sck_i/sck_o/sck_t ports with cfgclk, cfgmclk, eos, and preq. STARTUPE2 doesn’t function in behavioral simulation at all, so the transfer could never complete. Regenerating the IP with STARTUPE2 disabled restored the standard SCK ports and the test passed.

Both were configuration faults inside a vendor IP rather than logic errors, and neither was visible from the error message alone.
